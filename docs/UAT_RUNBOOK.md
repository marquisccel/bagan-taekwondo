# Runbook UAT — alur operator semi-prestasi

Dokumen ini adalah panduan uji penerimaan pengguna (UAT) untuk operator drawing. Semua langkah
dilakukan lewat antarmuka web; tidak perlu memanggil API secara langsung. Seluruh data contoh
bersifat rekaan dan tidak memuat NIK.

## 0. Persiapan (dilakukan fasilitator)

1. Jalankan PostgreSQL 16, API, worker, dan aplikasi web (lihat `README.md`). Worker wajib berjalan:
   pembuatan drawing dan ekspor PDF/XLSX dikerjakan oleh worker.
2. Siapkan satu turnamen yang sudah memiliki set aturan dan data registrasi hasil impor.
   Untuk uji lengkap (sampai LOCK dan PUBLISH) set aturan harus berstatus `ACTIVE` dengan seluruh
   batas maksimum toleransi ditetapkan panitia. Set aturan sementara (`provisional`) sengaja **tidak
   dapat dikunci**: langkah 12 akan ditolak dengan pesan yang jelas. Itu perilaku yang benar.
3. Siapkan tiga identitas (ID pengguna) untuk turnamen tersebut:
   - **Petugas Drawing** (`DRAWING_OFFICER`): membuat drawing, memindah/menukar peserta, mengajukan tinjauan.
   - **Delegasi Teknis** (`TECHNICAL_DELEGATE`): menyetujui, mengunci, menerbitkan, mengamendemen.
   - **Penonton** (`VIEWER`): hanya melihat.
4. Autentikasi produksi belum ada. Aplikasi memakai identitas pengembangan: masukkan ID pengguna di
   halaman awal. Untuk berganti peran, gunakan pemilih persona di bilah atas.

## 2. Yang perlu dicatat penguji

- Langkah yang tidak dapat dilakukan, pesan yang membingungkan, atau kata yang tidak dipahami.
- Apakah dokumen PDF cukup padat dan terbaca untuk meja pertandingan dan peninjauan komplain.
- Kasus di mana kualitas pengelompokan yang ditandai server (kuning/merah) tidak sesuai dengan penilaian
  panitia — sertakan kategori dan peserta yang terlibat.

## 3. Di luar cakupan UAT ini (ditunda)

- Bobot berat badan untuk Poomsae semi-prestasi (menunggu keputusan panitia).
- Kategori Pasangan/Beregu semi-prestasi (menunggu definisi aturan pengelompokan).
- Ekspor XLSX per kategori.
- Autentikasi produksi.

## 4. Catatan teknis untuk fasilitator

- Pemindahan/penukaran hanya diterima pada revisi berstatus DRAFT. Setelah PUBLISHED, ambil jalur
  **Amend**; setiap revisi baru melewati ulang tinjauan → persetujuan → kunci → terbit.
- Alasan operator wajib bila server menilai perubahan menurunkan kualitas (kuning). Pelanggaran aturan
  wajib (merah, mis. pool melebihi ukuran maksimum) selalu ditolak dan tidak dapat diakali dengan alasan.
- Semua keputusan kualitas dihitung server dengan logika mesin drawing yang sama dengan pembuatan
  drawing; antarmuka hanya menampilkan hasilnya.
