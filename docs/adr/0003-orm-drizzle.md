# ADR-0003: Drizzle ORM, SQL migrations, invariants enforced in SQL

- Status: Accepted (2026-09-11)

## Context

The schema carries safety rules that must hold even if application code is wrong or someone uses
`psql` directly: append-only audit, frozen revision content, one official revision per category,
no duplicate entry per revision, Technical-Delegate-only overrides. Commands also need explicit
row locking and optimistic-concurrency updates.

## Decision

- **Drizzle** for the typed schema and queries; migrations are **plain SQL files in the repo**
  (`packages/db/migrations`), generated by drizzle-kit and reviewed like code.
- Constraints that SQL can express are **CHECK / UNIQUE / FK constraints** in the schema.
- Rules that need other rows are **PL/pgSQL triggers** in a hand-written migration
  (`0001_invariant_triggers.sql`).
- Database enums are generated from the domain arrays (`packages/db/src/schema/enums.ts`).
- Every SQL state machine has a **parity test** against its TypeScript twin.

## Consequences

- Defense in depth: the application validates first (good errors), the database refuses what must
  never happen (last line).
- A CHECK constraint that evaluates to NULL passes. Phase 1 found four such bypasses; every
  nullable comparison now uses `IS TRUE`, `coalesce` or an explicit `IS NOT NULL`, and each has a
  regression test.
- Migrations run on PostgreSQL 16 (production target) and PGlite (fast tests, PostgreSQL 18).

## Alternatives rejected

- **Prisma** — less control over locking statements and raw SQL triggers in migrations.
- **Invariants only in application code** — a single bug or manual SQL session could corrupt an
  official result.

## Enforced by

`packages/db/src/schema.db.test.ts` (56 tests), run on PGlite always and on PostgreSQL 16 when
`DATABASE_URL` is set; SQL↔TypeScript parity for revision lifecycle, registration status and the
overridable-issue list.
